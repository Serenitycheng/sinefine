# 云端游戏存档

在「存档」页手动读取云端进度，或先预览本地快照再上传。同一游戏账号只有一个云端位置；上传会在确认后替换旧快照。读取不会改变本地游戏，恢复前仍会自动保留「恢复前的进度」。本地自动保存、浏览器备份与文件导入导出不依赖云服务。

## 部署前置条件

1. 沿用现有 Supabase 游戏账号服务与服务器环境变量：`SUPABASE_URL`、`SUPABASE_ANON_KEY`、`SUPABASE_SERVICE_ROLE_KEY`、`FATE_VAULT_SECRET`。它们只在服务器配置，不要使用 `NEXT_PUBLIC_` 前缀，也不要写入存档。存档功能本身不要求账号保存 AI 密钥。
2. 先应用已有的 `supabase/migrations/202609070001_cloud_connections.sql`，再应用 `supabase/migrations/202609260001_game_saves.sql`。
3. 部署包含 `/api/fate/save` 的应用版本。新表启用 RLS，撤销匿名用户和普通登录用户的直接访问；仅服务器角色有权限读取表或调用写入函数。不要另加允许浏览器直接修改此表的策略。

本地应用已与用户创建的独立测试项目 `Sinefine-recovery` 完成真实联调：迁移、注册登录、云端读写、并发版本保护和访问权限通过验证。应用尚未上线部署；完整记录见[第 9 条验收](../../docs/verification-step-9.md)。未配置时页面提供现有游戏账号入口，并保留全部本地存档能力；缺少表或函数时返回可重试的错误，不会退回不受保护的直接写入。

新测试项目可在 SQL Editor 运行 [setup-development.sql](../supabase/setup-development.sql)：该文件由上述两份迁移按顺序合并为一个事务，末尾列出四张业务表作为结果核对。执行目标为文件头指定的测试项目；不用于原有生产项目。若迁移源文件变更，应重新生成合并文件。

## 接口与并发保护

- `GET /api/fate/save`：服务器使用现有账号会话验证身份，返回 `{ username, slot }`。空位置为 `slot: null`；已有位置包含 `{ backup, revision, updatedAt }`。
- `PUT /api/fate/save`：仅接受同源 JSON 请求。正文是 `{ backup, expectedRevision, expectedAccount }`。`backup` 必须通过 `parseFateBackup`；请求体按实际 UTF-8 字节限制在 5 MB 内，即使缺少或伪造 `Content-Length` 也不会绕过限制。
- 数据库的防御性大小约束为 8 MB，给 JSONB 转文本时增加的空格留出余量；玩家上传限额仍是请求体 5 MB，避免接近上限的有效存档在规范化后被误拒绝。
- 首次保存使用 `expectedRevision: null`，数据库单条 `INSERT ... ON CONFLICT DO NOTHING` 保证双端首次创建只有一个成功。覆盖时必须传用户已经查看的正整数版本，数据库单条条件 `UPDATE` 比较版本并递增。禁止先读后无条件写入。
- 并发冲突返回 `409 / conflict`；确认期间账号切换返回 `409 / account_changed`。界面清除旧确认状态，要求重新读取并再次选择，不自动重试覆盖。
- 写入函数的用户 ID 完全来自服务器已验证的会话，客户端不能指定其他账号。时间戳来自数据库。所有成功与错误响应都设为 `Cache-Control: private, no-store`、`Vary: Cookie`。

存储仅包含解析后重新构造的游戏备份，不保留提交体中的额外连接配置。这里没有读取或解密 AI 连接密钥，也不会消耗模型额度。未知服务器错误只返回通用提示，不返回内部服务错误或凭据。

PostgreSQL JSONB 不接受 NUL 空字符或孤立的 UTF-16 代理项；接口会检查解析后备份的全部字符串，发现这些内容返回 `400 / invalid_backup`，不会静默删改台词或误报云端服务故障。完整的表情符号和正常换行可原样保存。

## 玩家操作

1. 在两台设备登录同一游戏账号；打开存档页，选择「读取云端进度」。
2. 上传时选择「准备上传当前进度」，对照本地快照、目标账号、旧云端快照及其保存时间，再明确确认上传或替换。发送的是准备时冻结的快照；后续本地变化需要重新准备。
3. 恢复时选择「预览恢复这份云进度」，查看现有恢复预览后，再选择「保留当前进度并恢复」。写入本地失败时保留原进度；浏览器不能持久保存时仍显示已有的临时存档提示。
4. 云端冲突或超时后重新读取。超时可能发生在服务器已保存之后，因此不会把失败响应当成「云端肯定未变化」，也不会自动补发覆盖。

云端只保留最新一份快照，替换前可直接选择「下载云端快照」保留旧文件，不需要先恢复本地。重要阶段建议同时下载文件。退出账号不会删除云端快照；删除 AI 连接也不等于删除游戏进度。

## 验证

运行 `node scripts/run-tests.mjs`。`tests/fate-cloud-save.test.ts` 使用可注入的内存后端，覆盖鉴权、同源、严格备份解析、密钥字段排除、实际字节限额、用户隔离、首次创建和覆盖的双端冲突、私有缓存、异常保护，以及沿用恢复前备份流程。测试不会联系 Supabase 或真实模型。

离线测试验证接口对原子后端的使用约定；真实 PostgreSQL 函数与权限已在独立开发项目验证。部署到其他环境后仍应重验：用两个同账号会话读同一版本，一端保存后另一端收到冲突；首次空位置也只允许一个会话创建成功。
